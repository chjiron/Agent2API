# 上游同步契约（本 fork 维护流程）

> 本仓库是 [aimod-cc/Agent2API](https://github.com/aimod-cc/Agent2API) 的二次开发 fork：
> 在维护自研功能（路由组等）的同时，持续吸收上游的版本迭代。
> 本文固定两件事的流程：**怎么把上游合进来**、**哪些改动永远不进上游 PR**。
> 发版流程（五处版本号同步、tag、Release、两条人工红线）沿用 `agent.md`，本文不重复。

## 1. Remote 分层

| remote | 指向 | 用途 |
|---|---|---|
| `origin` | `chjiron/Agent2API` | 自己的 fork —— **所有推送只去这里** |
| `upstream` | `aimod-cc/Agent2API` | 上游 —— **只 fetch，永不 push**（push URL 已置 `DISABLE_NO_PUSH` 防误推） |

## 2. 分支角色

| 分支 | 角色 |
|---|---|
| `main` | 发版分支：只在发版时从 `beta` 前进（合并 → 打 tag → 推 `origin`） |
| `beta` | 集成分支：日常改动、上游合并都先落这里 |
| `feat/*` | 临时功能分支，完成后合回 `beta` |

## 3. 例行：把上游合进来

```bash
git switch beta
git status --short        # 必须干净再开始
git fetch upstream --tags
git merge upstream/main   # 真 merge，保留上游提交历史
# 有冲突按第 4 节口径解；随后重建入库产物，与合并一起提交：
npm --prefix desktop-tauri/ui-islands run build
npm --prefix desktop-tauri/i18n run build
git add -A && git commit  # 产物变化并入本次合并（自动合并成功时即一次后续提交）
git push origin beta
```

- 跟踪的是上游 `main`（已发布的稳定线）；上游 `beta` 是它的集成分支，等它发布后再跟进即可。
- 推送 `beta` 会触发 `frontend-artifacts` 闸：它重建产物并要求与入库内容**逐字节一致** —— 忘了重建就会红。

## 4. 解冲突的三条固定口径

| 冲突位置 | 口径 |
|---|---|
| 五处版本号（`package.json` ×2、`desktop-tauri/src-tauri/Cargo.toml`、`server/Cargo.toml`、`tauri.conf.json`） | 取本 fork 的（`--ours`）；号段规则见第 5 节 |
| `desktop-tauri/i18n/i18n-src/**` | 键取**并集**；同名键以已翻译的为准 |
| 入库产物（`desktop-tauri/ui/islands/**`、`desktop-tauri/ui/i18n/**`） | **不手工合并**：任取一侧后按第 3 节命令重建覆盖 |

## 5. 本 fork 的版本号

- 本 fork 用自己的号段，核心号**始终大于上游当时的最新正式版**：上游 3.0.x 时本 fork 从 **3.1.0** 起；上游追平（发布 3.1.0）后本 fork 跳到 3.2.0，依此类推。
- 不能与上游同号：更新检查按三段数字比大小，同号或更小会让用户收不到本 fork 的更新。
- 发版时五处版本号必须同改（清单见 `agent.md` 第 4 节），tag 打 `vX.Y.Z` 并推 `origin`。
- 若上游日后出现与本 fork 同名的 tag，`git fetch upstream --tags` 会拒绝覆盖本地的（符合预期，不影响分支合并）；要查阅上游那一版另行单独取：`git fetch upstream refs/tags/<tag>:refs/upstream-tags/<tag>`。

## 6. 本 fork 私有改动（永远不进上游 PR）

1. `DEFAULT_REPO` 指向本 fork（`desktop-tauri/src-tauri/server/src/server/core/update/version.rs`）
2. 本 fork 的版本号与 tag
3. 本文档
4. 若日后决定「与上游版共存」才做的产品标识差异（installer identifier / 端口 / 配置目录）

## 7. 把功能 PR 回上游

上游接受外部 PR，但**只收 base = `beta`**（见上游 `agent.md` 第 1 节）。流程：

```bash
git fetch upstream
git switch -c upstream-pr/<主题> upstream/main   # 从上游干净切出，不要从 beta 切
git cherry-pick <功能提交…>                       # 不带第 6 节的私有改动
npm --prefix desktop-tauri/ui-islands run build
npm --prefix desktop-tauri/i18n run build
git add -A && git commit                          # 产物与源码同源
git push -u origin upstream-pr/<主题>
gh pr create --repo aimod-cc/Agent2API --base beta --head chjiron:upstream-pr/<主题>
```

规矩（摘自上游 `agent.md`）：

- PR 的 base 选 `beta`，不选 `main`；
- PR 回复若由 AI 代笔，末尾单独一行加 `🤖 本条回复由 AI Agent 生成`（英文场合再补 `Generated by an AI agent.`）；
- 提交里不要带 AI 共同作者 trailer（上游合并时会摘除）；
- 大功能先开 issue 对齐、拆成小 PR 再动手，避免做完整套改动却被架构意见推翻。

## 8. 本 fork 的 CI 与分发

- 推 `v*` tag 到 `origin` 触发与上游同款工作流：`build.yml`（Windows NSIS / macOS universal / Linux 服务端包，产物只挂 workflow artifact）与 `docker.yml`（GHCR 镜像恒推；Docker Hub 需自配 `DOCKERHUB_USERNAME` / `DOCKERHUB_TOKEN`，不配自动跳过）。
- GHCR 镜像地址自动跟随本仓库（`ghcr.io/chjiron/Agent2API`）；**新包默认私有**，首次推送后需在包设置里手动改 Public。
- 发版收尾沿用 `scripts/release.sh`（`gh repo set-default` 已指到本 fork）。
- 工作流已在 fork 上注册完毕（`build` / `docker` / `frontend-artifacts` / `warm-cache`）；日后新增 workflow 文件后若未出现在 Actions 列表，向默认分支推一次包含该文件的提交即可注册。
